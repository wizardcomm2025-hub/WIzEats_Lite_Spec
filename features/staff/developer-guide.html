Staff management

How waiters and chefs are added, listed and switched on or off. Three API endpoints sit behind the app's User Management screen, plus a panel page for super admins.

v1 scope

Four use cases: see the staff list, add a staff member, switch one on or off, and edit users in the panel. See the README. The spec records today's behaviour plus targets (re-synced 2026-11-24): STAFF-D1 is fixed in code; STAFF-D2, D3, D5, D6 are To fix; STAFF-D4 stays accepted.

How it works end-to-end

The owner opens UserManagement. The app posts /api/staff/getStaffDetails, and the server returns the restaurant's waiters and chefs. Add Staff posts /api/staff/create, which inserts an active user with PIN 123456 and mustChangePin. The new member signs in through AUTH and sets their own PIN. The Active switch posts /api/staff/update with isActive, which the server writes to users.status (working since 2026-11-17). In the panel, admin/user-management lists every user and edits name, role and status through /admin/user/update.

What matters where you sit

POS API

  • No role checks; no rate limits. Target (X-D1): create / update owner only; waiters and chefs get only their own row from getStaffDetails.
  • create: the role can be any text; no uniqueness rule, so a used phone gives a 500. Target (STAFF-D3): role chef / waiter; used phone → 422.
  • update: rule isActive (boolean) → users.status; returns the updated user. User::find(hex2bin($userId)) with no restaurant filter (STAFF-D2); invalid hex gives a 500. Target: only waiters / chefs of the caller's restaurant, else 404.
  • Target (STAFF-D5): create and switch-on refuse a second active user of the same role — 422 You can have 1 active chef and 1 active waiter.
  • fetch: scoped to the caller's restaurant and to the waiter / chef roles.

Data — MySQL

  • users.phone is unique across all restaurants.
  • Roles compare without regard to case (utf8mb4_unicode_ci). The app stores Chef / Waiter.
  • The panel update doesn't set updated_at.

POS app

  • The one-chef, one-waiter limit lives in staffLimits.ts and is checked only by Add Staff; the switch allows activating (target STAFF-D5: block it with the limit toast).
  • UpdateStaffPayload sends isActive; the slice applies the change locally on success.
  • Non-owners fetch only their own row; only the owner sees the switch and Add Staff.

Super-admin panel

+ Add User calls an undefined openAddModal(). The table's switches have no listener. Only the edit dialog saves. Pages show 3 users each. Target (STAFF-D6): validate name / role / status; 404 for unknown ids. Not held to the staff limit.

Integrations

None. New staff aren't notified.
