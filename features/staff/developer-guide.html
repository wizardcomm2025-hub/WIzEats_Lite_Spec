Staff management

How waiters and chefs are added, listed and switched on or off. Three API endpoints sit behind the app's User Management screen, plus a panel page for super admins.

v1 scope

Four use cases: see the staff list, add a staff member, switch one on or off, and edit users in the panel. See the README. The spec records today's behaviour; STAFF-D1 to D4 keep the current rules as accepted risks.

How it works end-to-end

The owner opens UserManagement. The app posts /api/staff/getStaffDetails, and the server returns the restaurant's waiters and chefs. Add Staff posts /api/staff/create, which inserts an active user with PIN 123456 and mustChangePin. The new member signs in through AUTH and sets their own PIN. The Active switch posts /api/staff/update with isActive, but the server requires status, so the switch fails. In the panel, admin/user-management lists every user and edits name, role and status through /admin/user/update.

What matters where you sit

POS API

  • No role checks; no rate limits.
  • create: the role can be any text; no uniqueness rule, so a used phone gives a 500.
  • update: User::find(hex2bin($userId)) with no restaurant filter (STAFF-D2). The response is always data: null. Invalid hex gives a 500.
  • fetch: scoped to the caller's restaurant and to the waiter / chef roles.

Data — MySQL

  • users.phone is unique across all restaurants.
  • Roles compare without regard to case (utf8mb4_unicode_ci). The app stores Chef / Waiter.
  • The panel update doesn't set updated_at.

POS app

  • The one-chef, one-waiter limit lives in staffLimits.ts only.
  • UpdateStaffPayload sends isActive (STAFF-D1).
  • Non-owners fetch only their own row; only the owner sees the switch and Add Staff.

Super-admin panel

+ Add User calls an undefined openAddModal(). The table's switches have no listener. Only the edit dialog saves. Pages show 3 users each.

Integrations

None. New staff aren't notified.

Accepted risks (do not "fix" without a new decision)

  • STAFF-D1: the app's Active switch always fails with The status field is required.
  • STAFF-D2: any signed-in user can rename or switch off any user of any restaurant.
  • STAFF-D3: any role can create staff with any role text, and there is no server-side limit; a used phone gives a 500.
  • STAFF-D4: the fixed first PIN 123456.
  • AUTH-D2: switching a user off blocks only the next sign-in.
