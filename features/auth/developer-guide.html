Feature developer guide · AUTH

Sign-in & PIN

How owners, waiters and chefs get into the POS app: phone number, 6-digit PIN, a session token that lasts until logout, and an e-mailed reset when the PIN is forgotten.

v1 scope

Seven use cases: check a phone, sign in with PIN, reset a forgotten PIN, change PIN, log out, resume or end a session, and the legacy OTP / register endpoints. See the README. This spec records today's behaviour — decisions AUTH-D1 to D10 keep the current rules on purpose; AUTH-D11 is the one change to build.

How it works end-to-end

The app calls checkPhone; a known number moves to the PIN step, a new one goes to onboarding. loginPin checks status and PIN and creates a Sanctum token. The app stores it and routes by approval, mustChangePin and role. Every later call carries the token; RestaurantTenantMiddleware binds the user's restaurant. logout deletes that token; a 401 on any non-auth call makes the app sign out locally.

What matters where you sit

POS API

  • Routes in routes/api.php under auth; services PinService, OtpService, AuthService.
  • PIN endpoints answer with success, not status.
  • Rate limits: checkPhone, loginPin, forgotPin only. changePin and the legacy endpoints have none.
  • No role checks anywhere in AUTH.

Data — MySQL

  • users.phone is unique across all restaurants. pin is hashed by the model cast.
  • Tokens: personal_access_tokens, never expire, one per sign-in.
  • Reset sends the mail first, then replaces the PIN.

POS app

  • PhoneLoginScreen (phone and PIN steps), ChangePinScreen, LogoutDialogs.
  • RootNavigator picks Auth / Pending / Change PIN / Main.
  • The axios interceptor ends the session on 401 except for /auth/ URLs.

Super-admin panel

Not touched. Approval and user on/off decided there change what AUTH shows (ONB, ADM).

Integrations

E-mail PinMail to the restaurant's address for resets. Errors go to the Google Sheets error log.

Accepted risks (do not "fix" without a new decision)

  • AUTH-D1: legacy verifyOtp accepts 123456 for any phone, no rate limit.
  • AUTH-D2: switching off a user or restaurant only blocks the next PIN sign-in.
  • AUTH-D3: tokens never expire.
  • AUTH-D4: PIN change / reset leaves other devices signed in.
  • AUTH-D5: 500 responses may carry exception text.
  • AUTH-D6: anyone who knows a number can trigger Forgot PIN; it also works for switched-off users.
  • AUTH-D7: changePin has no rate limit.
  • AUTH-D8: the API reveals whether a phone is registered.

The one change to build

AUTH-D11: legacy register must create the restaurant and its owner together or not at all. Two parallel calls with the same new phone give one type: "register" and one type: "verify" for the same user — never a 500, never an empty restaurant. Test: AUTH-07-D18.
