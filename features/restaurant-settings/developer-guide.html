Restaurant profile & settings

How a restaurant's details and settings are read and changed: one details endpoint that also carries zones and tables, one update endpoint behind the app's Profile screen, and two unvalidated panel forms.

v1 scope

Three use cases: view the profile, edit it in the app, and edit it in the panel. See the README. The spec records today's behaviour; RST-D1 to D4 keep the current rules as accepted risks.

How it works end-to-end

The app calls /api/restaurants/showDetails at start-up, on resume, and on Home and Orders. It gets the restaurant row, restaurantConfig, and the active zones with their tables and running order IDs. ProfileScreen maps that to a form with restaurantToForm. On Save it posts the whole form to /api/restaurants/updateDetails. RestaurantService::updateDetails writes the validated fields in one transaction, and the app merges the reply or re-reads the record. In the panel, admin/restaurant.blade.php posts JSON to /admin/restaurant/update and /admin/restaurant/config/update, which write whatever is sent.

What matters where you sit

POS API

  • No role check and no rate limit on either endpoint.
  • Only fields in RestaurantProfileRequest are used. enableKot and the misspelt invocePrefix pass validation but never reach a column (RST-D2).
  • taxPercent has no rule. serviceChargePercent needs exactly two decimals.
  • Service errors return Failed to update restaurant details / Failed to fetch restaurant details with no exception text.

Data — MySQL

  • A field sent as null is written as NULL. A NOT NULL switch then fails, and the whole transaction rolls back.
  • The order_channels updates use orderChannelId = 1/2/3 against binary(16) IDs and match nothing (RST-D1).
  • Tax is copied onto each new order. Existing orders keep theirs.
  • HasBinaryUuids hex-encodes any 16-byte string that isn't plain printable ASCII (finding F2).

POS app

  • Visible switches: Takeaway, Discount, Show KOT Number on Bill (and the KOT name). The others are commented out but still sent as held.
  • Every save sends serviceChargePercent: null and companyAddress: null (RST-D2).
  • On a phone, the Account section (Profile) shows for every role (RST-D3). The tablet rail shows it to the owner only.
  • Restaurant IDs are compared with Number() in belongsToSession, mergeRestaurant and loadRestaurantCache. Check this against hex IDs (finding F1).

Super-admin panel

No validation. A missing field is written as NULL. Errors show nothing, because res.json() fails silently. An unknown restaurant ID gives a 500 on the page and on the config save. The page's title copy says Analytics / Category Overview.

Integrations

None. The QR ID is a UPI ID rendered as a QR on Bill Payment.

Accepted risks (do not "fix" without a new decision)

  • RST-D1: the Takeaway, Delivery and Room Service switches never change the order channels. Home always offers all four.
  • RST-D2: an app save clears the service charge and company address. The KOT switch and invoice prefix can only be changed in the panel.
  • RST-D3: any role can save settings, including the UPI ID customers pay to.
  • RST-D4: almost no validation in the API or the panel. Negative tax is stored, and bad numbers or long text give a 500.
  • AUTH-D2: switched-off users and Pending / Rejected restaurants keep access.
