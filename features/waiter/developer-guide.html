Waiter — ready orders & dashboard

Ready Orders (KOTs the kitchen finished), marking a KOT delivered, and the waiter dashboard.

v1 scope

Three use cases: see ready orders, mark a KOT delivered, and the waiter dashboard. See the README. The spec records today's behaviour; WAIT-D1 to D3 keep the current rules as accepted risks.

How it works end-to-end

Ready Orders polls waiter/ready-kots every 15 s for status-4, un-picked KOTs. Delivered to Customer posts waiter/updatePickedUpStatus/{kotId}, and the app moves the card to an in-memory Delivered tab. The dashboard posts waiter/dashboard for the caller's order counts and today's top items.

What matters where you sit

POS API

  • Both KOT endpoints return raw binary kotIds, so a non-empty reply fails JSON encoding with a 500 (WAIT-D1).
  • The pick-up update uses the path text as is (hex never matches), has no role, restaurant or stage check, and its reply lists every restaurant's picked-up KOTs (WAIT-D2).
  • totalOrders has no date filter; top items count fulfilled orders from today only (WAIT-D3).

Data — MySQL

  • Pick-up sets isPickedUp / pickedUp_at; status stays 4.
  • kots has no restaurantId; only the ready list scopes through order_items.

POS app

  • Errors are never shown; a failed list looks empty, a failed confirm leaves the card.
  • The Delivered tab is memory only (lost on restart or sign-out).
  • Revenue, average and turnover are hidden on the dashboard.

Super-admin panel

None.

Integrations

None.

Accepted risks (do not "fix" without a new decision)

  • WAIT-D1: ready list 500s when non-empty; hex pick-up never matches.
  • WAIT-D2: no pick-up rules; reply spans all restaurants; Delivered tab not persisted.
  • WAIT-D3: Total Orders is all-time; top items only today's paid orders.
