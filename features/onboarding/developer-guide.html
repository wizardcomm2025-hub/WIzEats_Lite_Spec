Feature developer guide · ONB

Onboarding & approval

How a new restaurant joins: a profile form, one transaction that creates the restaurant, owner and starter data, a PIN by e-mail, and a super admin's Accept or Reject in the web panel.

v1 scope

Four use cases: register a new restaurant, wait for approval, approve or reject, and the legacy token path of the setup endpoint. See the README. The spec records today's behaviour; ONB-D1 to D4 keep the current rules as accepted risks.

How it works end-to-end

Login's phone step sends a new number to RestaurantProfileScreen. It posts to /api/restaurants/setup without a token. RestaurantService::onboard creates the restaurant (Pending), the owner (random PIN, mustChangePin), the config with a unique restaurantCode, zone Main Hall with Table 1–4 and four order channels, all in one transaction; then mails the PIN and the admin notice. The super admin clicks Accept / Reject in admin/index, which posts to /admin/update-status/{id} and mails the owner. The app's PendingApprovalScreen re-reads approval via showDetails and moves on once Accepted.

What matters where you sit

POS API

  • /api/restaurants/setup is public with an optional token; no tenant middleware; 10 / min per IP.
  • Validation messages for the profile fields are Laravel's defaults (The restaurant name field is required.); phone messages are custom.
  • Errors return Failed to onboard restaurant with no exception text.

Data — MySQL

  • Six tables in one transaction; mails only after commit.
  • The zone upsert is keyed on restaurantId alone — it renames the restaurant's first zone.
  • isApproved is written as posted by the panel.

POS app

  • Only the Takeaway switch is visible; active and KOT are sent on, delivery and room service off.
  • The token in the setup response is discarded; the owner signs in after approval.
  • Approval refresh runs only when isOnboardingDone is true.

Super-admin panel

Accept / Reject buttons only while Pending; no confirmation; no message after the click. Only onboarded restaurants are listed.

Integrations

PinMail (onboarding), the plain admin notice to ADMIN_EMAIL, and RestaurantStatusMail. All failures are logged, never shown.

Accepted risks (do not "fix" without a new decision)

  • ONB-D1: any token can re-run setup and overwrite its restaurant, even a waiter's on an approved restaurant.
  • ONB-D2: the approval endpoint stores any value and can reverse a decision.
  • ONB-D3: a mistyped e-mail or lost PIN mail has no recovery path.
  • ONB-D4: legacy owners with onboarding not done are stuck on the Pending screen.
  • AUTH-D2: approval is enforced only by the app's screens, not the API.
