Feature developer guide · RPT

Reports / analytics

The owner's Dashboard: period figures, top sellers, channel mix, trends and the CSV export.

v1 scope

Three use cases: view the dashboard, see trends, export the report. See the README. The spec records today's behaviour; RPT-D1 to D3 keep the current rules as accepted risks.

How it works end-to-end

The screen posts three period reports with filter_type and the trend with trend_type on every focus. Export posts get-all-items and get-all-orders for today and writes CSV files to Downloads.

What matters where you sit

POS API

  • Summary, channels and trends count paid orders only; Top Selling and the items export count all lines (RPT-D1).
  • UTC days; last_30_days is the calendar month; trend sorting and week numbering quirks (RPT-D2).
  • get-all-orders returns raw binary IDs and 500s when non-empty; no role checks (RPT-D3).

Data — MySQL

  • Revenue is Σ orders.grandTotal, as sent at billing (BILL-D1).
  • Turnover counts orders with a tableId; app orders have none (ORD-D2).

POS app

  • Only owners see the Dashboard.
  • The export reports success even when a file wasn't written; CSV values aren't quoted.

Super-admin panel

None (its own statistics are ADM).

Integrations

None.

Accepted risks (do not "fix" without a new decision)

  • RPT-D1: paid-only figures vs all-lines Top Selling; client-sent revenue.
  • RPT-D2: UTC days, calendar-month "30 Days", trend ordering, all items in Top Selling.
  • RPT-D3: orders export 500s; unescaped CSV; any role reads revenue.
