Kitchen (chef)

The chef's KOT tabs, moving a KOT from Pending to Ready, and the chef dashboard.

v1 scope

Three use cases: see KOTs by stage, move a KOT through its stages, and the chef dashboard. See the README. The spec records today's behaviour plus targets (re-synced 2026-11-24; no KITCH code changed): KITCH-D1 to D3 are To fix.

How it works end-to-end

A chef signs in and lands on Kitchen Orders. Each tab posts chef/pending-kots with its status (0, 1, 3, 4) and polls every 15 s. A card's button posts chef/update-status/{kotId} with the next status. The dashboard posts chef/dashboard for today's counts of KOTs the chef last changed.

What matters where you sit

POS API

  • getPendingKots returns raw binary kotIds (and tableId / roomId), so any non-empty list fails JSON encoding: 500 Malformed UTF-8 characters (KITCH-D1). Target: hex IDs plus kotNumber and orderNumber.
  • updateKOTStatus uses the path text as is: hex never matches, yet it answers 200 (KITCH-D1). Target: hex lookup within the restaurant, 404 KOT not found.
  • No role, restaurant, range or stage-order checks; out-of-range values are written before the 500 (KITCH-D2). Target: chef only; 0–4 (422); allowed path only (409 Invalid status change); stage times kept.
  • The dashboard counts by chefId and today's created_at only (KITCH-D3). Target: the restaurant's KOTs of the day; accepted = Preparing, Completed or Ready.

Data — MySQL

  • kots has no restaurantId; the list scopes through order_items.
  • Each update keeps only the new stage's time; the other two become NULL. No "ready at" time.

POS app

  • Errors are stored but never shown; a failed list looks like an empty one.
  • Tab badges are hard-coded to 0. The card title is KOT #<kotId>, not the KOT number (target: the number — KITCH-D1).
  • The dashboard checks role === 'Chef' (case-sensitive); the rest of the app ignores case (KITCH-D3).

Super-admin panel

None.

None. The WhatsApp status message is on orders/update-status (DLV).
