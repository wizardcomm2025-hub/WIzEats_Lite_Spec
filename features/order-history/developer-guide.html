Feature developer guide · HIST

Order history

The Live and History tabs of Order History, with their filters and search.

v1 scope

Three use cases: see live orders, see past orders, filter and search. See the README. The spec records today's behaviour plus targets (re-synced 2026-11-24): HIST-D1 is fixed in code (2026-11-18); HIST-D2 and HIST-D3 are To fix.

How it works end-to-end

Each tab posts its endpoint (orders/orderHistoryLive, orders/orderHistory) with the same filter body. Live returns all running orders; History pages paid orders and adds payments, the bill and KOTs to each row.

What matters where you sit

POS API

  • The channel filter is channelCode, validated against order_channels.channelCode and matched upper-cased (HIST-D1 fixed 2026-11-18).
  • Live ignores search, payment type and paging, and uses UTC days; History uses IST days (HIST-D2). Target: Live lists every running order, applies channel and search, adds orderDateTime.
  • Both sort by created_at, newest first (since 2026-11-18). History works out Paid / Partial / Unpaid from the payments.

Data — MySQL

  • Payments are folded into one GROUP_CONCAT string per order and split again in PHP (target: loaded as rows — HIST-D3).
  • History runs a bill and a KOT query per row.

POS app

  • The filter sends the channel's channelCode (orderHistory.filters.ts).
  • Live cards show Sub Total because Live rows carry no bill.
  • The Live Bill Payment button opens Bill Payment (BILL-D2 fixed). Target: Live hides the date chips and the payment-mode filter.

Super-admin panel

None.

Integrations

None.

Accepted risks (do not "fix" without a new decision)

  • HIST-D2 (part): Live cards show Sub Total, also for a billed order.
  • HIST-D3 (part): loose search (LIKE, wildcards not escaped); a bill and a KOT query per History row.
